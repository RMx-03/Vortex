# Code quality and comment standards

Apply these conventions to new and changed code, with review effort proportional to the change. Runtime requirements below describe acceptance criteria for the [planned architecture](docs/architecture.md); the scaffold does not yet implement inference. Use [CONTRIBUTING.md](CONTRIBUTING.md) for review, verification and Git conventions.

- Prefer explicit typed contracts, one state owner per mutable resource, small modules and single-responsibility functions. Annotate public parameters and return values using Python 3.11-compatible types. Document units, optional values, mutability and ownership transfer; keep untyped external data at validated boundaries and justify any `Any`. Avoid mutable defaults and introduce protocols or abstractions only for an actual boundary, such as a fake versus device executor. Type hints do not replace runtime input validation.
- Validate request limits before accepting work. Bound queues, channels, sequence slots, token budgets and cache reservations; specify what happens when a limit is reached. Cancellation, failure and cleanup must be idempotent and testable. Define which component finalizes each resource so disconnect, timeout and execution failure cannot release it twice or leave it owned indefinitely.
- Handle expected exceptions at the boundary that can recover or translate them. Validate external input explicitly rather than relying on assertions; reserve assertions for internal invariants. Catch specific exception types, preserve useful causes and return actionable, sanitized errors. Use context managers or `finally` for cleanup; never silently swallow failures or catch `BaseException` to keep work running. In async code, propagate cancellation after cleanup, following [Python's cancellation guidance](https://docs.python.org/3.11/library/asyncio-task.html#task-cancellation).
- For concurrency, explain lock/synchronization assumptions and avoid hidden shared mutation. Define cache reservation/commit/rollback semantics. Identify state owners and allowed lifecycle transitions; do not rely on the GIL for compound state changes. Keep shared-state critical sections short; move slow I/O, device work and awaits outside state locks where possible. Document any necessary exception with bounded waits and deadlock reasoning. Use stable snapshots and revalidate before applying results. Bound retries and backpressure, and give background tasks an owner that observes failures and waits for shutdown.
- Keep separation of concerns explicit: API handles validation/transport/disconnects; scheduler chooses ordering and budgets; sequence manager owns request lifecycle; batch builder materializes iteration inputs; KV manager owns cache allocation; executor owns model/tensor/device operations; metrics observe these boundaries. CPU control logic must remain testable with a fake executor without a GPU, model download or HTTP server. Avoid embedding transport or model execution inside scheduling policy.
- For CUDA, describe tensor shapes, dtype, device, dimensions/units, ownership and memory lifecycle; don't equate metadata block allocation with a working physical cache. Account separately for weights, active KV storage and temporary workspace. Preserve sequence isolation; any approved shared-prefix cache needs matching inputs, explicit references and immutable storage or copying before mutation. Before reusing storage, establish that every device operation referencing it has completed or is safely ordered; cancellation of a CPU task does not establish that condition. Explain stream dependencies and allocation lifetime where non-default streams are used. Allocator-reserved memory differs from live tensor memory; `empty_cache()` cannot free live tensors. See [PyTorch CUDA semantics](https://docs.pytorch.org/docs/stable/notes/cuda.html). Require device tests for physical cache behavior.
- Comments explain **why, invariants, tradeoffs and non-obvious behavior**; never narrate individual lines or obvious syntax. Public docstrings explain the contract, parameter/return units, ownership, possible errors, blocking behavior and side effects where relevant. Update docs with behavior changes, remove stale comments and keep runnable examples accurate. Distinguish planned, implemented and measured behavior; do not require boilerplate comments for clear code.
- Avoid fabricated metrics or copied performance claims. Profile before optimizing. Define the timed interval and distinguish end-to-end latency from device time; use device events or appropriate synchronization for asynchronous GPU measurements, without adding global synchronization to the serving loop just to time it. Record hardware, model/tokenizer revision, source commit, versions, dtype, workload and settings; warm up, repeat and report distributions and uncertainty. Compare matched workloads, separate profiler overhead from benchmark results, and state when performance was not measured.
- Test correctness first (greedy reference tokens, cancellation, memory reclamation, sequence isolation), then benchmark. Use small deterministic fixtures, isolated tests and documented uncertainty. Seed applicable random sources, pin reference inputs/settings and use explicit numeric tolerances; a seed alone does not guarantee identical GPU results across devices or versions. Prefer controlled clocks and synchronization events over arbitrary sleeps. Tests must exercise observable contracts, limits and failure paths, not private implementation details. Use disposable repositories and synthetic credentials for Git/security tests; no network, real secrets or developer-state mutation. Label unrun GPU checks as NOT VERIFIED.
- Log request identifiers and sanitized counters, not prompts, token dumps, secrets or environment snapshots. Validate untrusted paths and avoid following symlinks outside approved roots. Keep private development context and tool instruction files outside public Git. Review data, notebooks, traces and generated artifacts before publication; ignore patterns and local guards do not replace review. Follow the [publication boundary](CONTRIBUTING.md#sourcedocumentation-boundaries).
- Do not introduce an unnecessary service, dependency, abstraction or GPU requirement. No runtime implementation begins before a corresponding approved feature spec/plan. Explain a new dependency or optimization's concrete need and maintenance cost. Respect existing contributor attribution and applicable disclosure rules; do not automatically append unsolicited co-author trailers or coding-assistant attribution to commits, PRs, comments or documentation.

An illustrative comment explains an ownership invariant rather than an assignment; it does not imply this runtime behavior is already implemented:

```python
# A cancelled request may still have queued device work using its cache.
# Do not make that storage available to another request until reuse is safe.
```
